# Aegis VPN — Android Client

Kotlin Android Studio project: login/signup screens, secure session storage,
a `VpnService` that runs Xray-core, and the two-phase verification flow you
specified. This is real source you open in Android Studio — I don't have an
Android SDK/emulator in my execution environment, so I could not compile a
signed `.apk` for you directly. Everything below has been reviewed carefully
and the JSON-generating logic was tested (see `docs/xray-config-test.md`
equivalent output in our conversation), but **you must build and test it on
an actual device before shipping it to users.**

## What's fully wired

- Login / self-service trial signup screens → call your backend's
  `/api/client/login` and `/api/client/signup`.
- `DeviceIdentity` — stable hashed device ID (not raw IMEI/serial).
- `SecureStore` — session token in `EncryptedSharedPreferences`, never the
  raw password.
- `XrayConfigBuilder` — parses the vless/vmess/trojan/shadowsocks links your
  backend returns into a complete Xray-core JSON config, including the
  domain-restriction + API-host-bypass routing rules for "package-limited"
  plans (e.g. a YouTube-only tier).
- `VerificationManager` — calls `/api/client/verify` once right after the
  tunnel comes up, then on a heartbeat, per your choice: **any** failure
  (explicit rejection or network error) triggers an immediate, authorized
  disconnect.
- `AegisVpnService` — establishes the TUN interface, starts Xray-core via
  the `V2RayVPNServiceSupportsSet` interface, and implements the kill-switch
  policy you chose: an *unexpected* core crash leaves the TUN interface open
  (so no packets get through at all) instead of falling back to the raw
  network, while a user-initiated or verify-triggered disconnect tears the
  interface down cleanly and restores normal connectivity.

## What you still need to add — and why I didn't fake it

**1. `libv2ray.aar` (Xray-core compiled for Android)**
Not on Maven Central. Build it yourself:
```bash
git clone https://github.com/2dust/AndroidLibXrayLite
cd AndroidLibXrayLite
# needs Go + gomobile installed
gomobile bind -androidapi 24 -o libv2ray.aar ./
```
Drop the resulting `libv2ray.aar` into `app/libs/`. Alternatively, extract a
`libv2ray.aar` from a recent, trusted [v2rayNG release](https://github.com/2dust/v2rayNG/releases)
(check its digital signature).

The exact Java method names Kotlin sees are generated by `gomobile` from the
Go interface, and can shift slightly between AndroidLibXrayLite versions —
I matched the current (2026) published interface exactly:
```go
func NewV2RayPoint(s V2RayVPNServiceSupportsSet, adns bool) *V2RayPoint
type V2RayVPNServiceSupportsSet interface {
    Setup(Conf string) int
    Prepare() int
    Shutdown() int
    Protect(int) bool
    OnEmitStatus(int, string) int
}
```
If your AAR build errors on the `AegisVpnService` overrides, check the
`.aar`'s decompiled interface (Android Studio will show you on a failed
build) — it's almost certainly just a version drift in this Go interface,
not a deeper problem.

**2. A tun2socks bridge**
`AndroidLibXrayLite` runs the Xray *proxy engine* — it does not itself turn
raw IP packets from a `VpnService` TUN file descriptor into SOCKS
connections. Real VPN apps (v2rayNG included) bundle a separate native
tun2socks binary for that (e.g. [xjasonlyu/tun2socks](https://github.com/xjasonlyu/tun2socks)
or `hev-socks5-tunnel`) as a `.so` in `jniLibs/`, and start it pointed at
the TUN fd and Xray's local SOCKS inbound (`127.0.0.1:10808`, already set up
in `XrayConfigBuilder`). I left this as an explicit `TODO` in
`AegisVpnService.startTunnel()` rather than guessing at a specific native
binary's exact command-line/JNI interface, since getting that wrong would
look like it works and then silently pass no traffic — worse than an
obvious gap.

**3. App icon**
Placeholder vector icon included so the manifest resolves. Replace via
Android Studio's Image Asset tool before release.

## Build

```bash
# from this directory, in Android Studio: File > Open
./gradlew assembleRelease -PapiBaseUrl=https://vpn-api.yourdomain.com
```

`apiBaseUrl` gets baked into `BuildConfig.API_BASE_URL` — point it at your
deployed backend (the `vpn-backend` project, behind HTTPS).

You'll need a release signing config (`signingConfigs` block in
`app/build.gradle.kts`) before `assembleRelease` produces an installable,
distributable APK — not included since that requires your own keystore.

## The two policies you chose, and their trade-offs

- **Verify failure → immediate disconnect, no grace period.** Simple and
  predictable, but means a single dropped heartbeat on a bad connection can
  kick a legitimate user off. If that turns out to be too twitchy once real
  users are on it, the fix is small: in `VerificationManager`, only treat
  explicit rejection codes (`SUSPENDED`, `EXPIRED`, `TRAFFIC_EXCEEDED`,
  `DEVICE_UNKNOWN`, `SESSION_EXPIRED`) as hard failures, and retry a couple
  of times on plain network exceptions before giving up.
- **Kill switch: strict, blocks all traffic until reconnected.** Implemented
  by *not* closing the TUN interface on an unexpected Xray-core crash — with
  nothing reading the tun fd, the OS can't deliver packets anywhere. This is
  the correct behavior for "never leak real IP," but means a crashed core
  leaves the user with zero connectivity (not degraded connectivity) until
  the app reconnects or they manually disconnect. `handleUnexpectedCoreDrop()`
  is where you'd add bounded auto-reconnect attempts.
